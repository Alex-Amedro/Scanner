## PROBLÈME N°1 : la robustesse entre seeds
À config identique, un seed réussit et l'autre échoue. VÉRIFIÉ : l'entraînement est DÉTERMINISTE à seed égal (`rep42` = `ctrl6` à la décimale),
donc ce n'est ni un défaut de code ni une erreur de reproduction : c'est un vrai effet du seed (1 réussite / 1 échec sur 2 seeds valides).
Ne PAS refaire le seed 43 (redondant). Pour estimer le taux réel : seeds 44, 45, 46 (~6 min chacun, MACHINE LIBRE, 8 envs). Tant que ce n'est pas réglé, aucun chiffre ne va dans le README sans >= 3 seeds.
Pistes (une à la fois, ~10 min par run, 2-3 seeds chacune) :
1. Mesurer le taux de réussite réel : `agile` seed 43, `ctrl6` seed 44.
2. Plus d'exploration (`ent_coef` > 0) ou taux d'apprentissage plus bas.
3. Départ « compétent » : pré-entraîner le réseau en imitant le pilote scripté (27-40 % de victoires sans apprendre) puis PPO.
4. Plus d'environnements par rollout (RAM permettant) pour lisser le gradient.
5. En dernier recours, honnête pour le CV : entraîner N seeds et garder le meilleur, en le disant clairement.

## Stratégie face à la variance (décidée le 3 octobre, à valider avec l'utilisateur)
L'entraînement est déterministe à seed égal ; un seed peut réussir (83 %) ou échouer (7 %). On en fait une propriété qu'on gère :
1. **Mesurer le taux réel** : >= 8 seeds de la config de référence (~6 min chacun, machine libre, 8 envs, vérifier `n_envs`/`steps`).
2. **Livrable fiable = sélection** : entraîner N seeds, évaluer, garder le meilleur. Le fichier modèle, lui, est parfaitement reproductible.
   Honnêteté : choisir sur un jeu de bâtiments (seeds 9000-9029) et RAPPORTER sur un autre (ex. 9100-9129) ; dire dans le README
   « N seeds entraînés, X % atteignent >= 70 % ».
3. **Outil à construire** (petit) : un lanceur « K seeds » qui coupe tôt les runs sans espoir (0 victoire vers 150k, c'est la signature
   des échecs), évalue les autres, classe, et sert pour CHAQUE étape suivante (nouvelles cartes, lacet, etc.).
4. **Réduire le taux d'échec** (chaque piste testée sur plusieurs seeds, pas un seul) : plus d'exploration, imitation du pilote scripté
   pour démarrer, plus d'envs par rollout.
5. Une nuit sans surveillance = 8 à 10 seeds ; la session doit rester ouverte (les tâches de fond s'arrêtent quand elle se ferme).

## Observation de l'utilisateur (3 octobre) : mouvements « à-coups », irréalistes
Il voit le drone partir à droite, s'incliner tellement qu'il doit repartir à fond à gauche, etc. Mesuré : commandes saturées (>0,95)
45 % du temps pour `ctrl6` (axe y), 39 % pour `agile`, 20 % pour `ctrl6_s2` (échec). Mécanisme : la consigne de vitesse à ±6 m/s, face à un
drone immobile, fait saturer l'inclinaison ; le réseau l'utilise comme ACCÉLÉRATEUR (bang-bang). Rien ne le décourage dans la récompense.
Pistes (à choisir avec l'utilisateur, une à la fois, comparées sur le seed 42 = 83 %) :
- A. Son idée : réduire `--max-tilt-angle-deg` (25-30) et/ou `--max-speed` (4-4,5). Réserves : `max_speed 3` a échoué 2 fois (cause inconnue) ;
  moins d'inclinaison = freinage plus long (35 deg : 4 m depuis 6 m/s ; 45 deg : 3,2 m).
- B. Pénalité sur les CHANGEMENTS de commande (`coeff * |a_t - a_(t-1)|`) : décourage le bang-bang sans filtrer (le lissage EMA a cassé
  l'apprentissage en v2.0, mais sous l'ancienne échelle de récompense -500 ; non retesté depuis). Petit ajout de code.
Critères : taux de victoire proche de 83 %, part de commandes saturées < 15 %, amplitude moyenne des changements de commande en baisse.
